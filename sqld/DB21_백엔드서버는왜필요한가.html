백엔드 서버는 왜 필요한가

4부 "백엔드가 DB와 대화하는 법"의 시작입니다. 프론트엔드(화면)만으로는 왜 안 되는지, 그 이유부터 확실히 짚고 갑니다.

STEP 1

이 가격, 누가 정할까?

노트북(1,200,000원) 결제 화면입니다. 정상적인 화면에는 가격을 바꿀 방법이 어디에도 없습니다. 그런데 "결제하기" 버튼을 누르면 실제로는 브라우저가 서버에 어떤 요청을 보낼까요?

💻
삼성 갤럭시북 노트북
1,200,000원
👆 버튼을 눌러서, 이 클릭이 실제로 어떤 데이터를 서버로 보내는지 "개발자도구"로 들여다봅시다.
🛠️ 개발자도구 — Network 탭 (실제로 전송되는 요청)
POST /api/pay HTTP/1.1 Content-Type: application/json { "product_id": "P003", "price": 1200000 }
🖊️ 이 노란 테두리 숫자, 직접 클릭해서 아무 값으로나 바꿔보세요. 개발자도구의 Network 탭이나 콘솔에서는 실제로 이렇게 요청 내용을 가로채서 값을 바꾼 뒤 전송할 수 있습니다. 화면에는 그런 버튼이 없어도, 요청 자체를 조작하는 건 막을 수 없습니다.
STEP 2

프론트엔드는 "사용자 손 안"에 있다

방금 가격을 마음대로 바꿀 수 있었던 이유를, 실제 코드로 직접 확인해봅시다. 같은 결제 기능이 프론트엔드와 백엔드에 각각 어떻게 나뉘어 있는지 보세요.

📱 프론트엔드 코드 (JS)
let price = 1200000; function checkout(){ fetch('/api/pay', { method: 'POST', body: JSON.stringify({ price: price }) }); }
🔓 이 코드는 사용자 브라우저에 그대로 다운로드됩니다. F12(개발자도구)를 누르면 이 코드를 누구나 읽고, 심지어 price 값을 콘솔에서 직접 바꿔서 실행할 수도 있습니다.
🖥️ 백엔드 코드 (Python)
@app.route('/api/pay', methods=['POST']) def pay(): product_id = request.json['product_id'] real_price = db.query( "SELECT PRICE FROM PRODUCTS WHERE PROD_ID=?", (product_id,)) charge_card(real_price)
🔒 이 코드는 우리 회사 서버 컴퓨터 안에서만 실행됩니다. 사용자는 이 코드를 볼 수도, 실행 중간에 값을 바꿀 수도 없습니다. 오직 "요청을 보내고 응답을 받는" 것만 가능합니다.
그래서 각자 정확히 무슨 일을 담당할까요?
📱 프론트엔드가 하는 일
  • 상품 정보를 화면에 예쁘게 보여주기
  • 사용자 입력(배송지, 카드번호 등) 받기
  • "결제하기" 버튼 클릭 시 서버로 요청 전송
  • 서버 응답을 받아 "결제 완료" 화면 표시
🖥️ 백엔드가 하는 일
  • 요청받은 상품의 진짜 가격을 DB에서 조회
  • 재고가 실제로 있는지 확인
  • 결제 금액을 최종 계산하고 카드사에 승인 요청
  • 결제 결과를 데이터베이스에 기록
💡 한 줄로 요약하면: 프론트엔드는 "보여주고 전달하는" 역할, 백엔드는 "판단하고 책임지는" 역할을 맡습니다.
STEP 3

"클라이언트가 보낸 값"을 다시 확인하는 3가지 실전 사례

모두 같은 패턴입니다 — 클라이언트가 보낸 값을 그대로 쓰지 않고, 서버가 데이터베이스에서 진짜 값을 다시 조회해서 비교합니다. 카드를 눌러 위험한 코드와 안전한 코드를 비교해보세요.

STEP 4

그럼 프론트엔드 검증은 필요 없을까?

아닙니다! 목적이 다를 뿐, 둘 다 필요합니다. 아래 회원가입 폼에 직접 입력해보면서 두 검증이 어떻게 다르게 동작하는지 확인해보세요.

💡 힌트: hong123, kim2024, abcd는 이미 가입된 아이디입니다. 이 중 하나를 입력하고 가입해보세요.
STEP 5

확인 퀴즈

다음 중 반드시 백엔드(서버)에서 처리해야 하는 것은?

오늘의 핵심 정리

기억할 것 3가지

  • 프론트엔드 코드는 사용자의 브라우저 안에서 실행되기 때문에, 개발자도구 등으로 얼마든지 조작될 수 있습니다 — 그래서 절대 신뢰할 수 없습니다.
  • 가격, 할인율, 재고 수량처럼 클라이언트가 보낸 값은 절대 그대로 믿지 말고, 서버가 데이터베이스에서 진짜 값을 다시 조회해서 비교해야 합니다.
  • 프론트엔드의 즉각적인 입력 검증(사용자 경험용)과 백엔드의 최종 검증(보안용)은 목적이 다르므로 둘 다 필요합니다.
